# Project Explanation Rules & Learning Mode

Whenever explaining any part of this project, adhere strictly to the following 15 rules:

1. **WHAT**: Explain WHAT the thing is in very simple, plain English.
2. **WHY**: Explain WHY it is being used in this project.
3. **HOW**: Explain HOW it actually works internally.
4. **CONNECTIVITY**: Explain how it connects with other parts of the project.
5. **LINE-BY-LINE CODE**: If code is involved, explain the relevant code line-by-line.
6. **COMPLETE FLOW**: Provide the complete end-to-end execution flow (e.g. User -> Frontend -> API -> Backend -> Database -> Response -> Frontend).
7. **FILE & FUNCTION TRACE**: Mention:
   - Which file is involved
   - Which function/component/class is involved
   - What calls it
   - What it calls next
   - What data is passed between them
8. **REAL-LIFE ANALOGY**: Use a simple real-life analogy whenever helpful.
9. **PROJECT EXAMPLE**: Give a concrete step-by-step example using this actual project codebase.
10. **TERMINOLOGY**: Define all technical terms before using them.
11. **FUNDAMENTALS FIRST**: Never skip fundamentals; build up step by step assuming beginner level.
12. **BIG PICTURE**: Explain the broader system/concept first, then connect back to the project.
13. **UNUSED / AUTOGENERATED CODE**: Point out any redundant, autogenerated, or unused files/code.
14. **NO ASSUMPTIONS**: Inspect actual files before explaining; base answers strictly on real implementation.
15. **NON-STANDARD APPROACHES**: Highlight if something is implemented differently from standard industry practice.
